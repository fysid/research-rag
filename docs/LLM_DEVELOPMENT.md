# Разработка Research RAG через LLM

Владелец задаёт цель и критерии готовности; LLM выполняет разработку, документацию, проверки и ревью. Инструкции агента: [AGENTS.md](../AGENTS.md).

## От задачи до принятого изменения

1. Создать Issue **LLM task**: проблема, границы, критерии приёмки, способ проверки.
2. Передать агенту ссылку на Issue и репозиторий. Агент читает инструкции и затронутый код.
3. Создать ветку `codex/<номер>-<имя>` от актуального `master`. Одна ветка — одна проверяемая задача.
4. Реализовать изменение. При изменении поведения тестировать результат, а не повторять реализацию. Для документации проверять текст, ссылки и формат.
5. Выполнить относящиеся к изменению проверки и независимое LLM-ревью, исправить существенные ошибки.
6. Открыть PR с базой **`fysid/research-rag:master`**. GitHub может автоматически предложить upstream — проверить базу перед отправкой.
7. Владелец принимает и объединяет PR; агент может объединить его по явному поручению. Автоматическое слияние не настроено.

В PR нужны цель, изменения, задача, фактически выполненные проверки, ограничения и откат. Агента/модель можно указать в описании; полный диалог и скрытые рассуждения не требуются. Секреты и пользовательские документы в PR не включать.

## Подготовка среды

Установка моделей, запуск приложения и проверка RAG относятся к этапу 2. Исходный проект фиксирует Node `18.18.0` и использует Yarn Classic. Обновление runtime проводить отдельно с проверками совместимости.

Пример ниже рассчитан на новый checkout, POSIX shell и отдельную тестовую БД. В существующем окружении сначала проверить данные и конфигурацию. Для sparse checkout перед установкой загрузить приложение: `git sparse-checkout disable`.

```bash
node --version
yarn --version
yarn install
yarn --cwd server install --frozen-lockfile
yarn --cwd collector install --frozen-lockfile
yarn --cwd frontend install --frozen-lockfile
yarn setup:envs
```

В корне upstream нет отслеживаемого `yarn.lock`, поэтому его установка пока не полностью воспроизводима. Root lockfile и переход на поддерживаемый Node — отдельная задача этапа 2. Существующие service lockfiles сохранять.

Заполнить локальные development-настройки, проверить `server/.env.development`, затем для новой тестовой БД:

```bash
yarn prisma:setup
yarn dev
```

`prisma:setup` генерирует клиент, применяет миграции и seed. `prisma:reset` удаляет содержимое БД и не нужен для обычной подготовки. Windows: Git Bash, WSL или Linux devcontainer, поскольку setup использует POSIX-команды. Парсер может требовать Chromium и системные библиотеки; пропуск скачивания Chromium не проверяет реальный парсинг.

## Проверки

После установки зависимостей и подготовки тестовой среды выбирать проверки по изменению:

```bash
yarn lint:ci
yarn test --runInBand
yarn prod:frontend
node extras/scripts/verifyPackageVersions.mjs
yarn translations:verify
git diff --check
```

Объяснять пропуски. `yarn lint` меняет файлы. UI работает на `http://localhost:3000`, API ping — `http://localhost:3001/api/ping`, collector — `http://localhost:8888/accepts`. Проверка документа → индекса → ответа с источником входит в этап 2.

## CI и автоматизация

**Repository checks** проверяет обязательные файлы и пробелы в diff. Upstream lint, тесты, версии пакетов и переводы сохраняют свои условия запуска и фильтры путей. Зелёная проверка документации не означает, что приложение протестировано.

Публикация образов, удаление QA-пакетов и обновление спонсоров ограничены исходным репозиторием `Mintplex-Labs/anything-llm`; для fork эти jobs пропускаются.

Issue сам по себе **не запускает LLM**. Агент запускается из выбранного пользователем инструмента. GitHub-бот, API-ключи, бюджеты и автономные релизы на первом этапе не подключены.

`CODEOWNERS` описывает владельца. Обязательность PR и CI задаётся фактически включёнными правилами ветки GitHub; наличие файлов само по себе их не включает.
